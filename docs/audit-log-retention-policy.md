## 1. Purpose

This document sets out how Tere Health captures, stores, protects, and eventually disposes of the audit trail generated by staff interactions with patient health information (PHI). It exists to satisfy:

- **HDC Code of Rights** — patients have the right to know who accessed their record.
- **HIPC 2020 Rule 5** (storage and security of health information) and **Rule 9** (retention limits).
- **Health (Retention of Health Information) Regulations 1996** — clinical records must be retained for **10 years** past the date of last contact with the patient. The audit trail is treated as an integral part of the clinical record and inherits the same retention obligation.
- **NEAC 2019 §12** — reviewer / regulator right of independent audit.
- **NZePS integration expectations** (Health NZ Digital Services) — every access to prescribing-related data is auditable.

## 2. What is captured

Every audit event is a row in the `audit_logs` table (Supabase Postgres, Sydney region). Row shape:

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key, generated server-side. |
| `event_type` | text | Non-null. e.g. `radiology_report_view`, `provider_mfa.enabled`, `encounter.call_initiated`, `research_data_export`, `view_phi`. |
| `provider_id` | UUID | Actor's provider row id, nullable only for pre-auth events (e.g. password reset request). |
| `provider_name` | text | Actor's display name at time of write (snapshot). |
| `provider_role` | text | admin \| billing_admin \| supervisor \| provider (snapshot). |
| `consultation_id` | UUID | Optional link to the consult the event relates to. |
| `patient_ref` | text | Non-identifying patient reference (e.g. first 8 of patient UUID) — deliberately not the full identifier. |
| `resource_type` | text | e.g. consultation, prescription, radiology_report, patient. |
| `resource_id` | text | ID of the touched resource. Not a foreign key — the target may be deleted, audit outlives it. |
| `reason` | text | For PHI-view events, one of a fixed allowlist: `billing_dispute`, `complaint_investigation`, `quality_audit`, `support_ticket_response`, `patient_request`, `clinical_care`, `other`. |
| `reason_notes` | text | Free-text elaboration on the reason. |
| `metadata` | jsonb | Event-specific structured detail (e.g. patch payload for encounter transitions, transaction id for payments). |
| `ip` | text | Requesting IP (`x-forwarded-for` first hop). |
| `user_agent` | text | Requesting User-Agent header (best-effort). |
| `created_at` | timestamptz | Non-null, default `now()`. |

Schema is defined in `supabase/features-migration.sql` and formalised in `supabase/2026-08-04_audit_logs_schema_reconcile.sql`.

### Event types currently written

- **PHI access:** `view_phi` (with subtypes recorded in metadata) — written by `PhiRevealGate.jsx` every time an admin reveals clinical detail behind the reason gate.
- **Radiology:** `radiology_report_view`, `radiology_report_update`, `radiology_report_mark_reviewed`, `radiology_report_archive`.
- **Encounter transitions:** `encounter.call_initiated`, `encounter.no_answer`, `encounter.complete_encounter` (see `api/_encounter-action.js`).
- **Provider security:** `provider_mfa.enabled`, `provider_mfa.disabled`, `provider_password_reset_requested`, `provider_password_reset_completed`.
- **Payments:** `windcave_refund` (dead, retained for historic rows only — Windcave has been removed; future Stripe refund audit events will be added under a `stripe_refund` event type when the refund flow is wired).
- **Research:** `research_data_export`.
- **Async:** `async_response`.

New event types are added by writing to `audit_logs` from any endpoint via the service-role Supabase client. All new writers must follow the column mapping documented in the file's header comment.

## 3. Where it is stored

- Primary storage: Supabase Postgres, project `xynwqfbnwpkyvovxdone`, region `ap-southeast-2` (Sydney).
- Backups: Supabase managed daily backups (7-day PITR window on the Pro plan).
- Long-term archive: **quarterly** snapshot of `audit_logs` exported as gzipped CSV to a private AWS S3 bucket in `ap-southeast-2`, encrypted at rest with SSE-S3. Retention on S3: 10 years matching HDC clinical-record retention. Access to the archive bucket requires MFA-gated IAM assumption; access itself is audit-logged in AWS CloudTrail (a separate, out-of-application trail — Tere staff cannot suppress it).

The quarterly archive is an *addition* to Supabase, not a replacement — Supabase remains the operational source of truth. Archive is for legal-hold and long-tail regulator queries when the operational database may have been pruned.

## 4. Immutability

- The `audit_logs` table is append-only enforced at three layers:
  1. **Application:** no endpoint issues UPDATE or DELETE against `audit_logs`. The only writer is the shared `.insert()` call in `api/_audit-log.js` and per-endpoint inserts documented in §2.
  2. **Row-Level Security:** only the service_role can access the table; the anon role has no policy granting SELECT/INSERT/UPDATE/DELETE.
  3. **Database triggers:** `BEFORE UPDATE OR DELETE` triggers on `audit_logs` raise an exception regardless of role. Even a service-role client cannot modify a historical row. See `supabase/2026-08-04_audit_logs_schema_reconcile.sql`.

Corrections to a mis-recorded event are made by writing a new event of type `audit_correction` referencing the original row's `id` in `metadata.corrects_id`. The original row is never edited.

Deletion of an audit row would appear as a schema-modifying operation (trigger drop) in Supabase logs — a very loud signal.

## 5. Who can access the audit log

| Role | Read | Write | Notes |
|---|---|---|---|
| Anonymous / patient | ❌ | ❌ | No route exists. |
| Provider (non-admin) | ❌ | ❌ | Providers do not query the audit log. Their own PHI accesses are recorded but not exposed back to them in-app. |
| Admin | ✅ (via `/api/audit`) | ✅ indirectly (via `/api/audit-log`) | Admin dashboard `AuditLogPanel` renders recent rows. Every admin *read* of the audit log is itself audit-logged. |
| Billing admin | ✅ (limited) | ✅ indirectly | Billing admin sees payment and support-ticket related events only. Clinical notes access events not filtered — but no filtering exposes clinical content because the row itself never contains full note text. |
| Supervisor | ✅ (own supervisees only) | ✅ indirectly | Read scope restricted by application logic to events involving providers under their supervision. |
| Regulator / HDC / OPC | On request | ❌ | Export process documented in §7. |
| Tere DBA (Patrick + Justin) via Supabase console | ✅ | ❌ (blocked by trigger) | Console access is itself logged in Supabase project-level audit logs. |

## 6. Retention period

- **Live retention in `audit_logs` (Supabase):** minimum 10 years from row `created_at`.
- **Archive retention on S3:** 10 years from the quarter the archive was generated.
- **Rationale:** matches the Health (Retention of Health Information) Regulations 1996 10-year floor for the clinical record. The audit trail is treated as an extension of the clinical record because it evidences who accessed it.

Rows are **not** deleted automatically. A retention sweep runs manually once per calendar year on 1 December, executed by the CMO, that:

1. Identifies rows with `created_at < now() - interval '10 years'`.
2. Cross-checks each row's `patient_ref` against the patients table to confirm the associated patient's last-contact date is also > 10 years old (a fresh contact resets the clock for that patient's records, per HDC guidance).
3. Confirms the S3 archive containing those rows exists and is intact (SHA-256 verified against archive-time manifest).
4. Only rows meeting *both* the age criterion *and* the patient-last-contact criterion are deleted. Deletion is done by executing `DELETE ... WHERE id IN (...)` after temporarily dropping the delete trigger, then re-creating it. The entire operation is itself audit-logged in a separate `audit_retention_sweeps` table.

If Tere ceases operation, the S3 archive is transferred (per the business continuity plan, §6.2 planned) to a nominated successor entity or, absent one, to the Office of the Privacy Commissioner for the residual 10-year period.

## 7. Providing audit records to regulators and patients

**Patient request** (their own record only): patient submits a written request via `hello@terehealth.co.nz`. Response within 20 working days (HIPC Rule 6). The exported record is a filtered `audit_logs` extract for events touching that patient's `patient_ref`, provided as a PDF summary.

**Regulator request** (HDC, OPC, MCNZ, Health NZ Digital, ACC integrity unit): scope-defined subset of `audit_logs` provided in CSV within the timeframe stipulated in the request. Export is generated from the Supabase console by an admin, packaged with a SHA-256 checksum, and delivered via a secure channel agreed with the regulator (typically HealthLink secure messaging or an OPC-provided SFTP endpoint).

Every regulator export is itself audit-logged as `audit_export.regulator` with the requesting body and scope in metadata.

## 8. Monitoring and integrity checks

- **Daily:** Supabase automated backup runs. Backup completion logged in project observability.
- **Weekly:** on-call engineer glances at the AuditLogPanel to confirm rows are still flowing (a silent audit failure is a compliance breach).
- **Monthly:** count check — new-row rate for each event_type against baseline (e.g. `encounter.call_initiated` should track consult volume within ±20%). Deviation triggers investigation.
- **Quarterly:** archive export to S3 (§3); SHA-256 manifest generated and stored inside the archive.
- **Annually:** end-to-end test — pick 5 recent PHI-view events from AuditLogPanel, verify each has the reason + reason_notes captured, and that the actor's role snapshot matches their current role (or, if it doesn't, that the change is legitimate).
- **Annually:** retention sweep (§6).

---

## 9. Breach of this policy

Any Tere staff member who:
- Deletes or modifies an audit row,
- Bypasses the reason gate (e.g. via direct SQL) to view PHI,
- Fails to submit a required regulator export within timeframe, or
- Accesses PHI without a legitimate `reason` from the allowlist

is subject to disciplinary action up to and including immediate termination of contract, MCNZ referral (if a clinician), and reporting to the Office of the Privacy Commissioner as required by HIPC.
