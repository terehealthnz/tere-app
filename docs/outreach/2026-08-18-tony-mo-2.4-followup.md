Thanks for confirming 2.1 passed. On the 2.4 — sorry for the runaround; last patch clearly missed whatever your Capricorn Cloud sender is prefixing MSH with. Deployed a much more defensive fix just now that handles the three most likely causes:

1. **UTF-16 encoding** — Capricorn Cloud has historically shipped 2.4 messages as UTF-16LE (with or without a BOM). Our reader was force-decoding as UTF-8, turning `MSH` into `M\0S\0H\0`, which fails the segment recognition. Body reader now auto-detects UTF-16LE / UTF-16BE / UTF-8 via BOM, plus a heuristic that re-decodes as UTF-16LE if the UTF-8 output is more than 20% null bytes (catches BOM-less UTF-16).

2. **Length prefixes or wrappers** — parser now scans for the first `MSH[|^]` occurrence and slices from there, so any unknown framing before the actual message header is dropped.

3. **Null bytes / MLLP** — belt-and-braces strip of `0x00`, `0x0B`, `0x1C`, and BOMs from the segment stream. HL7 batch protocol headers (`FHS`/`BHS`) are also transparently skipped.

Also, if we ever hit this class of problem again, the reject ack's MSA-3 now carries a hex + ASCII dump of the first 32 bytes we received (against the pre-decode buffer, so encoding info is preserved). That way you don't need to write me an email to hand off the diagnostic — it comes back in the ack itself.
